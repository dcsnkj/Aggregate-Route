# 使用说明

## 它是怎么工作的

Codex 的 provider 被指向本机 `http://127.0.0.1:8788/v1`，请求先到这个本地路由，
路由按请求体里的 `model` 查路由表，逐个候选网关转发，失败自动换下一跳：

```
路由表取候选 → 候选1 的各把 key 轮换 → 候选2 的各把 key 轮换 → … → 全失败透出最后一个错误
```

请求是**流式透传**的（SSE 分块转发），所以你在 Codex 里看到的还是逐字输出，不是等全部生成完再吐。

## 模型路由表是怎么来的

装配脚本（`setup/setup_router.py`）会：

1. 按 `~/.codex/router-sources.json` 从 cc-switch 里取各网关的 `base_url` 与密钥
2. 拉每个网关的 `/v1/models`
3. **逐个模型真发一次请求**校验，分五类：

   | 判定 | 含义 | 处理 |
   |---|---|---|
   | `ok` | 可用 | 放进模型选择器 |
   | `unsupported` | 404 不支持 / key 无效 | **从路由表里删掉**，留着只会每次白等 |
   | `nobalance` | 403 额度不足 | 保留作兜底，但**不放进选择器**（选了也白选） |
   | `overloaded` | 500 满载 | 保留并放进选择器（那是临时的） |
   | `timeout` / `net` | 探测不出结论 | 保留并放进选择器 |

4. 生成 `auto`（按 `auto_chain` 依次试）与"同名跨网关"的候选链
5. 写路由配置、模型目录，并在 cc-switch 与 `config.toml` 里挂上 `router` provider

> **为什么必须真发请求校验**：网关的 `/v1/models` 列表会骗人 ——
> 实测某个网关列了 17 个模型，真正能用的只有 1 个，其余在目标协议上全是 404。

## 单一入口（slug）

有些网关的模型名带斜杠（`nvidia/nemotron-3-ultra-550b-a55b`），
**Codex 的模型选择器不显示这类名字** —— 列表里会看不到它们。
这时给该上游配一个 `slug`，把它的多个模型合成一个入口：

```json
"nvidia": {
  "base_url": "https://integrate.api.nvidia.com/v1",
  "keys_file": "~/.codex/nvidia-keys.txt",
  "slug": "nvidia",
  "models": ["z-ai/glm-5.3-flash", "meta/llama-3.2-11b-vision-instruct"]
}
```

于是选择器里只出现 `nvidia` 一个，内部按 `models` 的顺序换用
（第一个不行就下一个）。**要放多模态入口时，只把实测支持图片的模型放进 `models`**，
否则轮到不支持图片的模型时，图片请求会直接报错。

## 跨模型兜底

同一个模型名在多个网关都有时，候选链是自动生成的（同名跨网关）。
但更多时候**别家没有同名模型**，这时用 `fallbacks` 显式指定"这个模型挂了就换谁的哪个模型"：

```json
"fallbacks": {
  "gpt-6-astra": [["nvidia", "nvidia/nemotron-3-ultra-550b-a55b"],
                  ["deepseek", "deepseek-flash"]]
}
```

于是 `gpt-6-astra` 的候选链变成：
`anyrouter/gpt-6-astra → nvidia/nemotron-3-ultra-550b-a55b → deepseek/deepseek-flash`。

**代价要说清楚**：兜底换的是**另一个模型**，输出风格和能力会变。追求"绝不空手而归"
就用它；追求"必须是指定模型"就别配。日志里兜底候选会标 `fallback`，看得出来是不是走了它。

## 只有 chat 接口的网关怎么办（协议桥接）

Codex **只支持 Responses API** —— `wire_api = "chat"` 已被官方移除，写上去直接报
```
Error loading config.toml: `wire_api = "chat"` is no longer supported.
```
而大量网关（NVIDIA NIM、多数 OpenAI 兼容中转）**只有 `/chat/completions`**。
所以路由内置了一层翻译（`router/chat_bridge.py`），上游协议由装配时自动探测：

| 探测结果 | 路由行为 |
|---|---|
| `/responses` 有端点 | `protocol = "responses"`，请求与 SSE **原样透传**（最省事、最无损） |
| 只有 `/chat/completions` | `protocol = "chat"`，**逐块翻译**：请求 `instructions + input[]` → `messages[]`；响应 `choices[].delta` → Responses 事件流 |

翻译覆盖的映射：

| Codex 发的（Responses） | 转成（Chat） |
|---|---|
| `instructions` | 一条 `system` 消息 |
| `input[]` 里的 `message` | `user` / `assistant` 消息（文本压成字符串，图片转 `image_url`） |
| `input[]` 里的 `function_call` | `assistant` 消息 + `tool_calls[]` |
| `input[]` 里的 `function_call_output` | `tool` 消息（带上对应的 `tool_call_id`） |
| `tools[]`（function 类型） | `tools[]`（chat 形状；非 function 类型如 `local_shell` 会被丢掉） |

反过来，Chat 的流会被翻成 Codex 认识的事件序列
（`response.created` → `output_item.added` → `output_text.delta` / `function_call_arguments.delta`
→ 各 `*.done` → `response.completed`），`sequence_number` 严格递增 ——
**这些事件形状是照真实网关的回包定的，不是照文档猜的**，少字段 Codex 会解析失败。

已实测通过的三条路径：**纯文本**、**工具调用往返**（模型发 tool_call → Codex 执行 → 回传结果 → 模型给最终答案）、
**图片输入**（发纯红图，模型答「红色」）。

### 已知表现：「一直显示正在思考」

chat 上游的推理模型会把**思维链**放在非标字段 `delta.reasoning_content`，
而桥接层只转发 `delta.content`（Codex 只认 `output_text`）。
所以模型先长时间思考时，**界面会一直显示「正在思考」而没有任何内容** ——
这不是卡死，是它在想。日志里的 `reasoning_chars` 就是被丢弃的思维链字数。

本机 `nvidia` 入口就踩过：首选 `z-ai/glm-5.3-flash` 是推理模型，
用真实大提示（Codex 桌面端上万 token）时能沉默到分钟级。解决办法见下。

### 缓解办法：让上游别把时间花在思维链上

`extra_body` 可以把任意参数原样塞进 chat 请求体。对 NVIDIA 的推理模型，
`reasoning_effort: "low"` 实测能**关掉思维链**（首字 6.4s → 0.8s，思维链 0 字）：

```json
"nvidia": {
  "base_url": "https://integrate.api.nvidia.com/v1",
  "slug": "nvidia",
  "models": ["z-ai/glm-5.3-flash", "meta/llama-3.2-11b-vision-instruct"],
  "extra_body": {"reasoning_effort": "low"}
}
```

实测 `thinking=false` / `enable_thinking=false` / `reasoning_effort=none`
**都不行**（模型直接不输出任何内容）；**只有 `low` 有效**。
不同网关的有效参数不一样，得逐个试出来。

## 流被截断时不再「假装回答完了」

上游有时会在**没送完**的情况下断开（网关超时、连接被重置）。
旧行为是照常收尾 —— Codex 会把半截回答当成完整回答，**回合就此结束**，
表现就是「任务做到一半就停了，要手动点继续」。

现在的行为：

| 情况 | 路由动作 |
|---|---|
| 正常收完（见到 `response.completed`） | 日志 `truncated=False`，原样透传 |
| 上游中途断开（没见到终止事件） | 日志 `stream_truncated` + `truncated=True`；**补一个 `response.failed`** 事件，并把该 key 冷置（让重试换一把 key） |

`response.failed` 是 Codex 认识的终止事件，它收到后会走自己的重试逻辑
（`responses_retry`，最多 5 次），而不是把半截结果当成完成。

chat 桥接同理：拿不到 `finish_reason`/`[DONE]` 就不发 `response.completed`，改发 `response.failed`。

## 失败判定与重试策略

**会换下一跳的**：`401 / 403 / 404 / 408 / 409 / 425 / 429 / 5xx`，
等响应头超过 `header_timeout`（默认 30 秒），以及连接层错误。

**不会换的**：`400 / 413 / 422` —— 请求本身的问题，换哪家都一样，直接原样回给 Codex。

**全部候选都失败时**：把最后一个上游的真实错误透出去（而不是笼统 502），
所以 Codex 里显示的通常就是网关的原话。

## key 轮换与冷却

- **轮换**：每个网关一个轮询计数器，每次请求换一把 key 起步，避免总用同一把被单独限流。
- **冷却**：某把 key 刚失败就临时冷置 —— 额度不足 15 分钟、限流 2 分钟、5xx 与超时 1 分钟。
  排序时正常的排前面、冷却的垫底，**全部冷却时仍会逐个试**（不会因为都冷却就拒绝服务）。
- **观测**：日志里 `via` 字段就是实际用的那把 key：

  ```json
  {"event":"ok","via":"gw-a/model-x@…abc123","elapsed":5.4,"bytes":80716,
   "skipped":["gw-a/model-x@…def456"]}
  ```

**轮换能解决什么、不能解决什么**（实测结论，别夸大）：

- 能：同一秒里有的 key 报 500、有的返回 200 —— 轮换确实提高命中率，
  也挡住了单 key 的配额、限流、封禁。
- 不能：整个模型通道同时满载时，所有 key 一起失败，轮换救不了 ——
  这种情况要靠路由表里的**下一个网关**（把 `auto` 用起来）。

## 路由挂了怎么办

看门狗（`watchdog.py`）每 60 秒探一次端口，掉了就立刻拉回来，开机自启，
所以正常情况下不用管。生命周期：

| 时机 | 行为 |
|---|---|
| 每次系统登录 | 启动文件夹里的 `聚合路由.cmd` 拉起看门狗 → 看门狗拉起路由 |
| 运行中路由崩了/被杀 | 看门狗 60 秒内自动恢复（日志里会写 `路由掉线，已自动拉起`） |
| 关机/重启 | 下次登录自动恢复 |
| 想停掉 | 任务管理器里结束 `pythonw.exe`（下次登录又会回来） |

**Codex 报 `Reconnecting... waiting for network`，八成就是路由没在跑** ——
跑一下 `--doctor` 立刻知道是哪一环断了。

## 排查

**先跑这条**（一次看全：路由在不在、看门狗在不在、key 有没有变少、选择器有几个模型、
近一小时有没有全失败）：

```bash
python ~/.codex/router/codex_router.py --doctor
```

其它：

```bash
python ~/.codex/router/codex_router.py --routes    # 路由表
python ~/.codex/router/codex_router.py --keys      # key 数与冷却状态
python ~/.codex/router/codex_router.py --check     # 逐个候选 + key 真实探测（会真发请求）
```

日志（JSON 行，`event` 字段区分类型）：

| event | 含义 |
|---|---|
| `ok` | 成功；`via` 是实际用的 key，`skipped` 是被跳过的候选 |
| `cooldown` | 某把 key 被冷置 |
| `passthrough_error` | 直接透传的错误（请求本身的问题） |
| `all_failed` | 所有候选都失败，`tried` 里有每一次尝试的详情 |
| `watchdog` / `watchdog_start` | 看门狗拉起了路由 |
| `config_loaded` | 配置热加载（改了路由配置不用重启） |

## 加 key / 加网关

**加 key**：追加到 `~/.codex/router-extra-keys.txt`（一行一把，`#` 注释），
然后重跑一次装配脚本。

> **为什么推荐写这个文件、而不是只在 cc-switch 里加条目**：
> 实测 cc-switch 有时会把 provider 条目的配置改写成「当前 provider」的配置
> （`auth` 变成别的占位符），轮换池就会悄悄少一把 key。
> `router-extra-keys.txt` 是**独立来源**，装配脚本把它与 cc-switch 收集到的 key
> 合并去重，所以哪个可靠就写哪个。

**加网关**：在 `~/.codex/router-sources.json` 的 `upstreams` 里加一条，重跑装配脚本。

**改优先级**：改 `order`（同名模型默认优先走哪家）与 `auto_chain`（`auto` 的兜底顺序）。

## 已知限制

- 只在 **Windows** 上验证过；路由本体跨平台，自启（启动文件夹 / `.cmd`）是 Windows 的。
- 请求开始流式返回之后就无法再换候选了 —— 如果上游在流中途报错，
  只能交给 Codex 自己的重连机制，路由不会重新发起。
- `--doctor` 的 key 数量对比基于装配时写入的 `expected_keys` 基线，手工改配置后重跑装配即可。
